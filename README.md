# BACCHUS-SYSTEM

日本酒のラベル写真・保管場所・残量を管理するモバイル向けPWA。iPhone/Androidのブラウザから使えます。バージョン 0.3.0。

## 実装した機能

- 写真撮影・端末内で縮小、銘柄・酒蔵・容量・製造年月等を確認して登録
- Gemini・Claude・OpenAIから選べるAIラベル読み取り（テナントごとにAPIキー・モデルを設定、利用量の記録と月間上限）
- 複数冷蔵庫と自由入力の棚・区画、瓶単位の移動
- 300mlは1本消費、その他は1合＝180ml消費。端数は「残りを飲み切る」
- 開封日、残量、入荷・消費・移動履歴、後続変更がない操作の取消
- 銘柄・酒蔵検索、冷蔵庫フィルター、空瓶表示
- 個人用：IndexedDBに在庫・写真・履歴を保存、オフライン登録・検索
- 共用：認証付きAPI・サーバーSQLite。テナント（店舗・会社・家族など）ごとに在庫を分離し、テナント内の利用者で共有
- 全体管理者・テナント管理者・メンバーの3ロール。全体管理者はテナントの作成・削除、テナント内はテナント管理者が管理
- メールアドレスとパスワード、またはSSO（OpenID Connect）でログイン。テナントごとに方式を選択
- 監査ログ（ログイン・利用者・設定・冷蔵庫の変更）
- 冷蔵庫の追加・名前変更・削除（共用ではテナント管理者のみ）
- オフラインの共用操作は端末に保留し、通信復旧・更新・同期操作で再送
- 操作IDによる重複防止、瓶のversionによる競合検出、サーバーで操作と履歴を同時保存
- JSONバックアップ、個人用バックアップの検証付き復元
- 個人用から共用への在庫コピー（冷蔵庫・写真・開封日・残量、重複防止付き）

初期データは空です。「冷蔵庫」→「＋冷蔵庫」→「撮影して登録」で始めます。AI解析は任意で、手入力のみでも全在庫機能を使えます。

## 起動（Python 3.12以降、外部パッケージ不要）

```sh
git clone https://github.com/UeEmon/BACCHUS-SYSTEM.git
cd BACCHUS-SYSTEM
python3 -m server.app
```

PCで http://127.0.0.1:8000 を開きます。公開リポジトリのcloneにはGitHub認証は不要です。未設定でも個人用モードが動作します。

## Docker Desktop

```sh
cp .env.example .env
docker compose up -d --build
```

PCで http://localhost:8092 を開きます。`.env`は自動生成されないためコピーしてください。DBは`bacchus-data`ボリュームに保存します。`docker compose down -v`はDBを消すため通常は使いません。

## スマートフォンで使う

PWAのオフライン起動とホーム画面追加には、信頼された証明書によるHTTPS配信が必要です。PCのlocalhostに対する開発用例外は、携帯電話からPCのLANアドレスへアクセスする場合には適用されません。

1. サーバーの前段にHTTPSリバースプロキシを配置し、スマートフォンからアクセスできるホスト名を用意します。
2. バックエンドの8000（Dockerでは8092）へプロキシします。アプリとAPIは同じオリジンです。
3. iPhoneはSafariでアクセスし「共有」→「ホーム画面に追加」。Androidはブラウザのインストール機能を使用します。
4. 初回オンライン起動後にオフライン起動を確認してください。ブラウザのデータ削除で端末在庫・保留操作は消えます。

LAN上の別PCから開発確認する場合は`HOST=0.0.0.0 python3 -m server.app`、Dockerなら`.env`の`BIND_ADDRESS=0.0.0.0`を指定します。HTTPのLAN接続は画面確認用です。共用トークンや写真を送る運用はHTTPSで行ってください。

## 共用保存（テナント）の始め方

共用モードはテナント（店舗・会社・家族など）単位で在庫を分けて管理します。Python直接起動時は環境変数を設定してください（`.env`を自動ロードするのはDocker Composeのみ）。

1. 最初の全体管理者用トークンを生成します。

   ```sh
   python3 -c 'import secrets; print(secrets.token_urlsafe(32))'
   ```

2. `.env`に登録し、SSOを使う場合はサーバーの公開URLも設定します。

   ```dotenv
   BACCHUS_USERS='{"生成した24文字以上のトークン":{"name":"運営","role":"system_admin"}}'
   BACCHUS_PUBLIC_URL=https://sake.example.com   # SSOのリダイレクト先。HTTPSの公開URL
   BACCHUS_TRUST_PROXY=1                          # リバースプロキシ配下で監査ログに利用者のIPを記録する場合
   ```

3. `docker compose up -d`で反映し、アプリの「設定」→「運用者トークンで接続」でトークンを入力します。
4. 「テナント管理」でテナントを作成します。同時に最初のテナント管理者（名前・メールアドレス）を登録し、表示された一時パスワードを本人に渡します。
5. テナント管理者はメールアドレスと一時パスワードでログインし、新しいパスワードに変更してから、冷蔵庫・利用者・ログイン方式・AIを設定します。

全体管理者もメールアドレスとパスワードで使えるよう、「テナント管理」→「全体管理者」で追加できます（`.env`のトークンは初期設定と非常用に限定するのがおすすめです）。

### ロール

| ロール | できること | できないこと |
|---|---|---|
| 全体管理者 | テナントの作成（最初の管理者を含む）・名前変更・**削除**、テナントごとのAI月間上限（運営上限）、全体管理者の管理、システムの監査ログ閲覧、管理者がいなくなったテナントへの管理者追加（復旧用） | テナント内の利用者・在庫・冷蔵庫・AI設定の閲覧と変更 |
| テナント管理者 | 自テナントの利用者の追加・ロール変更・無効化・削除・パスワード再発行、ログイン方式（パスワード／SSO）、AI設定（サービス・APIキー・モデル）、AI月間上限、AI利用量・監査ログの閲覧、冷蔵庫の追加・名前変更・削除、個人用在庫の一括追加、すべての在庫操作 | 他テナントの操作 |
| メンバー | 自テナントのすべての冷蔵庫での登録・消費・飲み切り・移動・取消、AIでのラベル読み取り | 冷蔵庫の管理、利用者・設定の変更 |

権限はすべてサーバーで判定し、許可されない操作はHTTP 403で拒否します。画面には権限のある操作だけを表示します。個人用モードは端末内の利用のためロールはなく、冷蔵庫の管理もできます。

**テナントの削除**は全体管理者だけが行えます。確認のためテナント名の入力が必要です。利用者・ログイン状態・冷蔵庫・在庫・写真・履歴・AI設定・AI利用記録・テナントの監査ログがすべて削除され、元に戻せません。システムの監査ログには削除の記録が残ります。

### ログイン方式

テナント管理者が「管理画面」→「ログイン」で、テナントで使う方式を選びます（両方同時に有効にできます）。

- **メールアドレスとパスワード**：利用者を追加すると一時パスワードを表示します。初回ログイン時に変更するまで他の操作はできません。パスワードは10文字以上で、PBKDF2-SHA256（60万回）でハッシュ化して保存します。5回続けて失敗すると15分間ロックします。
- **SSO（OpenID Connect）**：Google Workspace・Microsoft Entra ID・Okta などのIDプロバイダーに対応します。テナント管理者がissuer URL・クライアントID・クライアントシークレットを登録し、画面に表示されるリダイレクトURI（`BACCHUS_PUBLIC_URL`＋`/api/auth/sso/callback`）をIDプロバイダー側に登録します。利用者はメールアドレスを入力して「SSOでログイン」を押します。登録済みのメールアドレスと一致する利用者だけがログインでき、初回にIDプロバイダーのアカウントと結び付けます（以降は同じアカウントのみ）。認可コードフローにPKCE・state・nonceを使い、IDトークンは発行元・宛先・有効期限を検証します（署名検証の代わりにHTTPSで直接受け取ったトークンのみを使います。OpenID Connect Core 3.1.3.7に基づく）。
- パスワードを無効にするとSSOのみになります（少なくとも一方は有効）。SAMLは未対応です。

ログイン状態（セッション）は12時間操作がないと終了し、最長30日です（`BACCHUS_SESSION_HOURS`で変更可）。セッションはそのタブを閉じると端末から消え、サーバーにはハッシュだけを保存します。ロール変更・無効化・パスワード再発行・削除をすると、その利用者のセッションはすぐに終了します。

`.env`の`BACCHUS_USERS`は固定トークンの利用者で、画面から変更できません。`system_admin`以外は「既定のテナント」に所属します（値が表示名だけ・以前の`"role":"admin"`はテナント管理者、`role`省略はメンバー）。

### AI設定と利用量（テナント単位）

AIのサービス・APIキー・モデルはテナントごとにテナント管理者が「設定」→「AIラベル読み取り（テナント）」で登録します。AIの利用料金はそのAPIキーの契約者に請求されます。キーはサーバーのDBにテナント別に保存し、在庫データやJSONバックアップには含めず、画面には末尾4文字だけを表示します。DBファイルにはキーが含まれるため非公開の場所に保管してください（DB内での暗号化は未対応）。

- **Gemini**（Google AI StudioのAPIキー）: 最新の安定版Flash-Lite → Flash → Pro。安定版がなければプレビュー版。
- **Claude**（Claude ConsoleのAPIキー）: 画像入力と構造化出力（JSONの形式保証）に対応した最新のHaiku → Sonnet → Opus。4.5世代より前は対象外です。対応モデルでは思考量を`low`に抑えます。Sonnet・Opusの一部では、安全上の理由で断られた場合にサーバー側の代替モデル（`fallbacks`）で再試行し、それでも断られたら手入力を案内します。
- **OpenAI**（OpenAI PlatformのAPIキー）: GPT-4.1以降の最新のnano → mini → 通常版。

「自動（推奨）」はラベルの文字を読める中で最も速く安価な系統の最新版を選びます。読み取り精度が悪ければ一覧（速く安価な順）から高性能なモデルを選んでください。自動選択中のモデルが提供終了（HTTP 404）になった場合は選び直して1回だけ再試行します。

**利用量の管理**：AIを呼び出すたびに日時・利用者・サービス・モデル・結果・入出力トークン数を記録します。テナント管理者は「管理画面」→「AI利用量」で今月の回数・トークン数・最近の利用を確認し、月間上限（回数）を設定できます。全体管理者もテナントごとに運営上限を設定でき、小さい方が適用されます。上限に達するとその月は手入力のみになり（HTTP 429）、回数は毎月1日（UTC）にリセットされます。

環境変数のAIキー（`GEMINI_API_KEY`・`ANTHROPIC_API_KEY`・`OPENAI_API_KEY`とモデル名、`AI_PROVIDER`）は、旧版から移行した「既定のテナント」だけが使えます。新しいテナントは画面で登録してください。

AI解析は利用者が「AIでラベルを読み取る」を押したときだけ、写真をサーバー経由で設定中のサービス（Google・Anthropic・OpenAIのいずれか）へ送信します。個人用の在庫DB全体を送ることはありません。APIの認証・課金・利用上限はチャットサービスの契約とは別です。

APIリファレンス: https://ai.google.dev/api/generate-content ・ https://platform.claude.com/docs/en/api/messages ・ https://platform.openai.com/docs/api-reference/chat

### 監査ログ

ログイン・ログイン失敗（理由つき）・ログアウト・パスワード変更、利用者の追加・変更・削除・パスワード再発行、ログイン方式・AI設定・AI上限の変更、冷蔵庫の追加・名前変更・削除、個人データの一括追加を、日時・操作者・対象・IPアドレスとともに記録します。テナント管理者は自テナントの記録を、全体管理者はテナントの作成・変更・削除と全体管理者の操作、存在しないメールアドレスでのログイン失敗を閲覧できます（新しい順に200件）。パスワード・APIキー・クライアントシークレットの値は記録しません。在庫の入荷・消費・移動は従来どおり「履歴」タブに記録します。

### 同期・競合

共用モードではサーバー接続後に利用します。オフライン時は前回のデータと保留操作を表示します。同期はアプリが開いている間に実行され、OSによるバックグラウンド実行は保証しません。同じ瓶を別端末で変更すると保留操作は競合として残り、勝手な上書きはしません。「同期」で再試行し、解消できない場合はバックアップ後に「保留操作を破棄して再取得」を選び、正しい操作を入力し直してください。

保存モードを切り替えても個人データと共用データは別々に保持します。共用モードの「設定」→「個人用の在庫を共用へ追加」で、端末の冷蔵庫・瓶・写真・開封日・残量をコピーできます。確認画面で共有対象を確認して実行します。既に移行した瓶は上書きせず、移行元も残します。過去の操作履歴は個人用に残り、共用には移行記録を追加します。冷蔵庫はIDで区別し、同名の異なる冷蔵庫を自動統合しません。1回の上限は100冷蔵庫・1,000本・約20MBです。移行後の二方向同期、共用から個人への移行、共用JSONのアプリ内復元は未実装です。共用DBはサーバー停止中にボリュームをバックアップするか、SQLiteのオンラインバックアップ機能を使ってください。復元時はサーバー停止中にDBを置き換えます。

`InventoryService`, `Bottle`, `ConsumptionPolicy`, `LocalRepository`, `ServerRepository`, `RecognitionService`, `LabelRecognizer`（サービスごとの`Gemini`・`Claude`・`OpenAI`）の責任を分離しています。表示に必要な値は容量mlを整数として保持し、数量と残量を混同しません。商品ごとに瓶の個体IDを発行するため、同銘柄の開封済み瓶・別の冷蔵庫の瓶も区別できます。

初版はネイティブFlutterではなくPWAであり、端末保存はSQLiteではなくIndexedDBです。

### サーバーDB（スキーマ v2）

| テーブル | 内容 | キー・制約 |
|---|---|---|
| `tenants` | テナント名・ワークスペースID・運営のAI上限 | `id` |
| `tenant_settings` | ログイン方式・SSO設定・AIキー・AI上限（テナント別） | (`tenant_id`, `key`) |
| `users` | メールアドレス（全体で一意）・ロール・パスワードハッシュ・SSO連携・無効化・ロック | 全体管理者だけテナントなし（CHECK制約） |
| `sessions` / `sso_requests` / `login_codes` | ログイン状態・SSOの途中状態・SSO後の一回限りのコード（すべてハッシュで保存） | 期限切れは自動削除 |
| `refrigerators` / `bottles` | 冷蔵庫・瓶（残量・容量・バージョン） | (`tenant_id`, `id`)、残量は0〜容量のCHECK制約 |
| `bottle_photos` | ラベル写真（瓶と別テーブル。履歴には複製しない） | 瓶の削除に連動 |
| `events` | 入荷・消費・移動などの履歴（追記のみ） | (`tenant_id`, `id`)、(`tenant_id`, `seq`) |
| `ai_usage` | AI呼び出しごとの利用者・モデル・結果・トークン数 | (`tenant_id`, `at`) 索引 |
| `audit_log` | 監査ログ | (`tenant_id`, `id`) 索引 |

テナント配下のデータは外部キーの`ON DELETE CASCADE`でテナント削除時にまとめて消えます。書き込みはすべて1トランザクションで、在庫操作は変更のあった行だけを更新します。旧版の形式（v0：1つの共用在庫、v1：テナントごとのJSON）は起動時に自動でv2へ移行します。現在の在庫取得（`/api/state`）は従来どおりテナントの在庫全体を返します。テナントあたりの在庫・履歴が大きくなる場合は、ページングとPostgreSQL等への移行を検討してください（テーブル設計はそのまま移せる形にしています）。

## 0.3.0 更新

AIラベル読み取りにClaudeとOpenAIを追加し、共用モードをテナント単位に変更しました。

**既存環境の移行**（更新前にDBをバックアップしてください。DBの形式が変わります）

1. 初回起動時に、それまでの共用在庫（冷蔵庫・瓶・写真・履歴）は自動で「既定のテナント」へ移ります。端末の保留操作もそのまま同期できます。
2. 既存のAI設定（画面で保存したキー・モデル）と環境変数のAIキーは「既定のテナント」で引き続き使えます。
3. `.env`の既存利用者はこのテナントのテナント管理者として、トークンで接続できます。メールアドレスとパスワードでのログインに移るには、`BACCHUS_USERS`に`{"name":"運営","role":"system_admin"}`のトークンを追加し、全体管理者として「テナント管理」→既定のテナント→「テナント管理者を追加（復旧用）」で管理者を登録します。以降の利用者はその管理者が画面で追加します。
4. SSOを使う場合は`BACCHUS_PUBLIC_URL`を設定します。自動選択は最も速く安価な系統（GeminiはFlash-Lite）に変わりました。既存の自動選択中のGeminiは、設定画面でAI設定を保存し直すと切り替わります（保存し直すまでは従来のモデルを使います）。既存のDocker環境は `git pull --ff-only` → `docker compose up -d --build` で更新します。PWAを開いたままの場合、新しいオフラインキャッシュは既存のアプリタブをすべて閉じて開き直すと有効になります。在庫データは保持されます。
